# brevo

Send transactional email from any address on a domain verified in Brevo, via Brevo's **official remote MCP server**. This is send-only infrastructure — it exists because Cloudflare Email Routing on `agentlabs.cc` only handles *receiving*, and Gmail/`gws` refuse to set `From:` to an address that isn't a verified Gmail send-as identity.

**Do not build a CLI or SDK wrapper for this.** Researched 2026-08-11: no maintained CLI covers this (see "Why MCP, not a CLI" below). Brevo publishes an official MCP server that wraps the full API, including transactional send — use it directly as a tool, the same way you'd use `gws` for Gmail/Calendar/Drive.

## When to use this vs `gws`

| Need | Use |
|---|---|
| Send **from** `info@agentlabs.cc`, `d@vibebrowser.app`, or any Brevo-verified-domain address | **brevo** |
| Anything where a **reply matters** — negotiation, support thread, back-and-forth | `gws` (Gmail) — replies to a Brevo send land via Cloudflare Email Routing in the routing target's inbox, **not** threaded back to you. Brevo is fire-and-forget. |
| Send from a Gmail-verified send-as address you already own | `gws` |
| Need to read/search existing mail | `gws` — Brevo has no inbox access |

If the task needs a threaded conversation (vendor negotiation, support back-and-forth), do **not** use Brevo — the recipient's reply will not come back to you through this tool. Send the opener with Brevo if the `From:` must be a company address, then tell the human where the reply will land (the Cloudflare-routed inbox), or use `gws` from a Gmail-verified identity instead.

## Prerequisite: domain verification

Before any address `@domain.tld` can be used as `--from`/sender, the domain must be verified in Brevo (SPF + DKIM records added to DNS). `agentlabs.cc` is on Cloudflare DNS (registrar is Spaceship, nameservers delegated to Cloudflare — confirm with `dig +short NS agentlabs.cc`), so verification means adding Brevo's SPF/DKIM TXT records via the Cloudflare dashboard or API, once, per domain. Check `mcp__brevo__*` sender/domain tools (see below) to confirm a domain is verified before composing — do not assume.

## Auth: the MCP token is NOT the standard API key

Brevo has two distinct key types under **Account → SMTP & API → API Keys**:

- **Standard API key** (`xkeysib-...`) — works for direct REST calls (`POST /v3/smtp/email` etc.), does **not** authenticate the MCP endpoint.
- **MCP server API key** — generated by checking **"Create MCP server API key"** when creating a key. This is the one the MCP server's `Authorization: Bearer` header needs. Confirmed by testing: pointing the MCP endpoint at a standard key returns `401 invalid_token: Invalid or expired OAuth session`.

Additionally, Brevo enforces **IP allowlisting per key** by default on new accounts (Security → Authorised IPs, `https://app.brevo.com/security/authorised_ips`). A key call from an unrecognised IP returns `401 unauthorized: We have detected you are using an unrecognised IP address ...`. Authorize the sending host's egress IP there before anything will work — this is a dashboard action, not something the MCP or REST layer can bypass.

### Where the key lives

- Bitwarden, collection `dev`, item **"Brevo - agentlabs.cc"** — custom field `BREVO_API_KEY`.
- Mirrored at `~/.env.d/brevo.env` (gitignored, dev-machine only) — `source ~/.env.d/brevo.env` before wiring the MCP server, the same pattern as `source ~/.env.d/bitwarden.env`.
- **Never** hardcode it, never commit it, never put it in an inline shell assignment that lands in `ps` output as a bare literal — read it via `$BREVO_API_KEY` after sourcing.

Unrelated pre-existing Brevo credentials also live in Bitwarden (`mkt-daemon/brevo-api-key`, `mkt-daemon/brevo-password`, `Brevo (vibebrowser)`) — those back Chatwoot's SMTP config and a separate `vibebrowser.app` sender identity. Don't reuse them for `agentlabs.cc` sends and don't touch them from here.

## Wiring the MCP server (one-time per machine)

```bash
source ~/.env.d/brevo.env   # or pull BREVO_API_KEY from Bitwarden (must be the MCP-scoped key, not the standard one)
claude mcp add --transport http --scope user brevo \
  "https://mcp.brevo.com/v1/brevo/mcp" \
  --header "Authorization: Bearer ${BREVO_API_KEY}"
```

Verify:

```bash
claude mcp list | grep -i brevo
# brevo: https://mcp.brevo.com/v1/brevo/mcp (HTTP) - ✔ Connected
```

`claude mcp add` redacts the header value in its own echoed output, and `claude mcp list` never prints it — safe to run without leaking the key into a transcript.

If you only need a subset (e.g. sender/domain management), Brevo also serves per-module endpoints at `https://mcp.brevo.com/v1/brevo_<module>/mcp` (e.g. `brevo_senders`, `brevo_domains`) — same auth. The full `brevo/mcp` endpoint is simplest for this skill's purpose and is what's wired above.

## Using it

Once connected, Brevo's tools appear as `mcp__brevo__*` in the agent's tool list — load the specific tool via `ToolSearch` (query e.g. `"select:mcp__brevo__send_transactional_email"` or a keyword search like `"brevo send"` / `"brevo senders"` if the exact name is unfamiliar) before calling it. Brevo's MCP is auto-generated from their full OpenAPI spec (~190+ tools across contacts, campaigns, CRM, transactional email, senders, domains, etc.) — do not guess a tool name, discover it with `ToolSearch` first.

Core loop for a business email:

1. **Check the sender is usable** — search/load the senders or domains tool (e.g. `mcp__brevo__list_senders` / `mcp__brevo__get_senders`) and confirm the `--from` address's domain shows verified/active **before** composing. Composing against an unverified sender will fail the send.
2. **Send** — the transactional-send tool takes `sender` (email + optional name), `to` (array of {email, name}), `subject`, `htmlContent` and/or `textContent`, plus optional `cc`, `bcc`, `replyTo`. This is a 1:1 mirror of `POST /v3/smtp/email` — see [Brevo's API reference](https://developers.brevo.com/reference/sendtransacemail) for the exact field shapes if a call is rejected.
3. **Confirm** — a successful send returns a `messageId`. Report that back, don't just assume success from a 2xx.

## Why MCP, not a CLI (research, 2026-08-11)

Checked before building anything, per the "don't reinvent the wheel" rule:

- **`@getbrevo/cli`** (official, npm/Homebrew) — real and maintained by Brevo, but scoped to **OAuth integration management**, not transactional sending. Wrong tool.
- **`Nardjo/brevo-cli`**, **`dollardeploy/brevo-cli`** (unofficial) — 0 stars, 1 commit each, missing `--cc`/`--bcc`/`--reply-to`/`--dry-run`/sender-verification checks. Not production-grade.
- **`sislelabs/mailctl`** — combines Cloudflare Email Routing + Brevo, closest in spirit, but 3 stars/1 commit, own YAML-config auth model (not Bitwarden/env-var), no documented cc/bcc/reply-to. Not worth depending on.
- **Brevo's official MCP server** (`mcp.brevo.com`) — real, documented at [developers.brevo.com/docs/mcp-protocol](https://developers.brevo.com/docs/mcp-protocol) and [.../docs/integration-guide](https://developers.brevo.com/docs/integration-guide), auto-generated from Brevo's OpenAPI spec, confirmed (Brevo's own docs) to cover transactional email send, not just contacts/campaigns/analytics. It plugs straight into the agent harness via `claude mcp add` — no dependency for us to maintain, no wrapper code, no build step. **This is what's wired above.**

Conclusion: no existing CLI meets the bar, and none was needed — the official MCP does the job with zero code of our own.

## Troubleshooting

| Symptom | Meaning | Fix |
|---|---|---|
| `401 invalid_token: Invalid or expired OAuth session` on `claude mcp list` | Wrong key type for the MCP endpoint | Generate a key with "Create MCP server API key" checked in Brevo dashboard; standard `xkeysib-...` keys don't work here |
| `401 unauthorized: unrecognised IP address ...` (seen via direct REST probe) | Key is IP-allowlisted and this host isn't on it | Add the host's egress IP at `https://app.brevo.com/security/authorised_ips` |
| Send tool call fails citing sender/domain | `--from` address's domain isn't verified in Brevo | Check senders/domains via the MCP tools first (step 1 above); add SPF/DKIM in Cloudflare DNS for that domain and wait for Brevo to re-verify |
| Reply from the recipient never surfaces to you | Expected — Brevo is send-only | Reply lands via Cloudflare Email Routing in whatever inbox that route targets; use `gws` from the start if you need the reply threaded to you |
| `claude mcp add` again returns "already exists" | Server already registered | `claude mcp remove brevo --scope user` first, then re-add with the corrected key |
