# The Workflow — how every development task is worked

Den's standing process for ANY development task (feature, fix, infra code), dictated 2026-10-31. The main session running the Supervisor owns the board. Each task is run end-to-end by ONE task subagent, which spawns its own stage subagents. This skill is the whole dev process: board layer + per-task pipeline. (`dev_tasks` was consolidated into `dev_workflow` 2026-10-31; the pull script keeps its path under `dev-tasks/scripts/`.)

**Goal (Den, 2026-10-31):** bring the product to a public release that can ship without fear — infra proven ready, every offered feature proven working live, never by audit alone. The release tag is the product owner's decision on live-verified readiness; proven readiness is the agent's job.

**Compliance is mandatory.** The task subagent opens this skill and runs Stage 0. Stage subagents inherit the task subagent’s claim, read their assigned stage, and execute only that stage; they never claim the task again, restart the whole workflow, or dispatch another task subagent. Every brief names the task subagent, this skill and the assigned stage. Work outside the pipeline is a process violation — stop and return to the task subagent. The backlog cron's dev work follows these stages too.

2. **Stall reflection** per row: *my stall* = a stage finished, the next never started (PR without review, clean review without merge, verdict without a fix agent) — name it plainly. *Den's gate* (money, sign-in, decision) or *external gate* (fleet, CI, third party) must be verified against the exact step and current evidence; it exempts only dependent work, not the whole task. Name the gate's unblock in one phrase.
3. **Push, same turn, no asking:** steer the existing live task subagent; dispatch only actionable unclaimed work under the Supervisor’s task-slot and priority rules, after claim checks or confirmed ownership transfer, briefed with `dev_workflow` and the exact stage owed. One line per push under the table. A status answer listing actionable stalled work without pushing it or recording the gate/capacity wait is a failed run of this skill.

### Starting a task

Order: (1) GitHub issue exists, with scope + acceptance criteria; (2) Work Log row created — no row, no start; (3) ONE task subagent dispatched to own the task end-to-end, within the Supervisor’s project-wide three-active-task limit, in priority order. The task subagent's first action is the Stage 0 claim; it runs Stages 1–6 by delegating substantive stage work and retaining ownership/gate verification — it coordinates and verifies, it does not implement inline. The main session never implements dev work inline and never lets a claimed task sit ownerless; it monitors task subagents via the Work Log and GitHub readbacks and intervenes on stalls.

**One task, one lead.** Each task has exactly one owning task subagent (its lead); a lead that ends without the task Done or Closed leaves a continuation receipt on the task record (what was blocking, what was done, what remains), and the Supervisor starts the next lead in the same run — or, only when the blocker is genuinely outside the Supervisor's power, the row goes to Blocked with the one reason on the row (see `dev-workflow-supervisor`, **Ownership and dispatch**). A completed lead's session never remains the owner of an In progress row. A gate that has its own Work Log row is a separate task with its own lead, never absorbed into a parent task's scope; related tasks coordinate through their records, not shared ownership.

Every stage brief names the owning task subagent, inherited claim and assigned stage, and carries: the goal, the issue, the Notion design/PRD links, prior decisions, the acceptance criteria, the permissions granted, a stopping condition. Every handoff returns: the result, the evidence, unresolved issues, the recommended next step — never chat memory alone.

### Keep the stage chain running

The task subagent owns the whole task, not just one stage. It spawns separate subagents for substantive stage work; the task subagent retains claims, handoffs and gate/merge verification, and remains responsible after each subagent reports. Use the runtime’s supported completion delivery or wait mechanism. A completion notification is a handoff, not task completion; cron and the user must not be needed to restart the chain. Keep one active stage subagent per task by default. Yield while that child runs; reserve runtime capacity for children before admitting task parents.

On every stage result: read back its artifact and acceptance evidence, update the persistent task record, then actually start the next allowed stage or send failures back through the runtime’s message/resume tool. Reporting the result or promising the next step is not continuation. A child saying PASS or Blocked is input to verify, not a terminal verdict. For Blocked, check the exact dependency and permitted alternatives, continue independent substeps, or record a concrete external gate with evidence, owner and resume condition. A gate stops only dependent work.

Before yielding, persist task-subagent ID, current stage, stage-subagent IDs and artifact links in the task record. On resume or task-subagent replacement, inspect those children: adopt/steer existing work if supported, or confirm it stopped before replacing it. Reload the task record, current ownership and fresh artifacts; never restart finished stages from chat memory. Address instructions to the actual stage subagent through available runtime tools. If delivery fails or no continuation mechanism exists, persist the exact next action and report that limitation to the Supervisor; never imply the chain is running.

Model choice per stage subagent: bounded work with clear checks → cheaper capable model; ambiguous architecture or hard debugging → stronger model. The reviewer is always a different agent from the implementer.

## Stage 0 — Claim (task subagent only, before stage work)

1. The task exists as a GitHub issue (create if missing, with scope + acceptance criteria).
2. Check nobody else is working it: issue comments, open PRs, commits from the last 48h. Parallel actors are real (Den's local agent, the fleet). **Another active claim → stand down, withdraw any claim you posted, report, pick different work.** Never race another actor on the same ticket.
   Attribution: bot authors (`vibesoftwareengineer[bot]`, `agentpodsoftwareengineer[bot]`) are shared credentials and prove nothing. Identify an actor only by a self-signed claim (branch prefix `codex/…`, a "Codex chat <uuid>" comment, an OpenCode `ses_…` claim) — and treat even those as self-reports.
3. The task subagent posts a public-safe claim comment as its first action: agent name + role (e.g. "Muse — task lead, VibeBrowser board push") + task/branch reference + scope, without private runtime/session identifiers — the raw runtime session UUID is stored only in the Work Log `Owner session ID` field, never in public comments. Read back the claim; store the exact runtime session ID only in the authorized Work Log ownership fields defined below. Mark In progress only after acknowledgment and evidence that execution started; a spawn receipt alone is insufficient. Update the issue at design-done, fix-shipped, merge.
4. **Ownership transfer (lesson 2026-10-31, #3271):** exactly ONE owning session per task. When Den moves a task to another chat: the old owner stops its agent FIRST (a stopped agent can leave a stray claim — name that risk), then hands over in one message: full brief + "you are the single owner now" + "check the issue for a stray claim from the stopped session". The receiver confirms ownership on the issue before working.

## Stage 1 — Context gathering (context subagent)

The task subagent spawns a context subagent. It reads the issue completely (body, all comments, linked PRs/issues, labels) plus the Notion design and PRD, and returns ONE context brief: what is asked, current status, prior decisions, acceptance criteria, existing evidence. Later stages reuse this brief, but refresh changed decisions, ownership, code SHA and blocker/run evidence before acting. Never work from the title alone.

## Stage 2 — Design (Notion is the home of design + PRD)

**Design depth by task type (Den, 2026-11-07 — simple fixes do not get a long architecture review):**
- **Feature** (new behavior or surface, or any change to a contract/invariant): the full Stage 2 below — design in Notion + independent design/architecture review; no implementation before PASS.
- **Bug fix:** light design — root cause + the design gap recorded (investigation track, step 2), with a short amendment to the design doc where one exists. NO separate design-verification loop — unless the fix changes a contract, invariant, or cross-service behavior, in which case it moves to the feature lane for design.
- **Simple fix / alert fix** (root cause known, change confined to one component, no contract/invariant change): NO design stage in most cases — root cause + the intended change in one short issue comment, then straight to implementation. Stage 4 review and Stage 6 validation still apply in full. If the work turns out not to be confined, the task subagent escalates it to the bug-fix or feature lane and says so on the issue.

1. Find the task's design + PRD in Notion. Read them.
2. **Design defined?** → spawn a design/architecture review subagent: it reviews the design's architecture against the ticket and PRD — complete? consistent? acceptance criteria defined? Gaps go back to the design, not into implementation guesses.
3. **Design missing?** → spawn a design subagent: it writes the design (approach, scope boundaries, acceptance criteria) into the Notion page, per the `dev_docs` skill (`~/workspace/custom-skills/dev-docs/SKILL.md`): 30-second read, concrete nouns and numbers. Then step 2 runs on it.
4. No implementation until the design exists in Notion and passes review.

## Investigation track (bug hunts, root-cause, verdicts)

No Stage 2 upfront — there is nothing to design yet.

1. Investigate to a root cause, with evidence. Separate verified from unverified.
2. **Bug found → the fix does not start until the design gap is recorded:** (a) find the design gap that allowed the wrong implementation (no design at all = the gap; say so); (b) record it at the depth of the task's Stage 2 lane — a Notion design-doc update for feature-lane work; an issue comment suffices for a simple/alert fix (no Notion round-trip); (c) fix through the normal stages, against the recorded gap; the review checks the fix against the design change that motivated it. After the fix merges, the Stage 5.5 Design/PRD sync check still runs — the repair covered the gap, the sync check covers everything else the fix changed.
3. No bug (works as designed, external cause) → record the verdict on the issue. If the investigation exposed a design weakness, step 2 applies to it.
4. **A verdict never dangles (weekly review, 2026-10-31):** every gap or follow-up named in a verdict leaves with a concrete artifact before the session ends — a filed follow-up issue (linked), a fix PR, or an explicit park naming the owner/gate. "Recorded for scheduling" is a dropped stage (it happened twice in one day: #5770's promised G1 ticket never filed; #5766's unwired dedup sat as prose while the alert re-paged hourly).

5. **Sibling sweep before closing a repeated shape (weekly review, 2026-11-02):** when a fix repairs one call site of a shape that can exist in siblings (a catch that clears state but misses a cancel/cleanup, a probe missing an expected status), grep every sibling call site for the same shape BEFORE the issue closes, and file/fix each hit in the same task. The friend-promo leak repeated 4 times in 2 days (#5848 → #5849 → #5851 → #5852) because each fix closed on its own site while the next site carried the identical leak.

Done right: the lxd-4 ZFS suspension (#5712) — root cause was a design flaw (pool as a sparse file on the host root fs); the durable fix changed the layout in the design/setup, not just the pool.

## When a stage cannot proceed

Before declaring Blocked, record `cause | current SHA/run/failed step | exact operation held | owner | next action | expected artifact`. Separate dependency, permission, access and execution failures from stale claims; an old pre-fix failure is not proof that current code fails. Check an authorized alternative and continue independent substeps. Do not wait for a release tag to run an independent workflow.

**Own the dependency:** inspect the current cause, then search the Work Log/issues for an existing root-cause repair. Reuse it and preserve its owner; otherwise create one scoped repair task with affected-parent links, evidence, acceptance criteria and the exact next step. Keep private runtime/session IDs in the authorized Work Log, not public issues/comments. Send this dependency to the main session running `dev-workflow-supervisor` for priority and task-slot admission; do not dispatch another task parent inside this task or bypass the three-task limit. Record the parent’s gate and resume condition, continue independent substeps, and release its slot only through the Supervisor after confirming no execution remains live. Ticket creation alone is not progress. The Supervisor must execute the authorized repair or record the specific approval/capacity wait; after verified repair evidence, resume this task at the owed stage and recheck its acceptance. Never weaken a test or change a contract solely to clear the blocker.

**Failed canary/CI stops release, not authorized repair.** Follow the Supervisor's failed-canary rule: at most one justified diagnostic rerun for suspected transience; a repeated/reproducible failure requires actual diagnosis and repair, independent review, regression and all required checks on the new SHA. Reuse the repair task and respect task-slot/ownership gates. Do not end at “stop and fix,” bypass checks, or increase timeouts without testing the cause; record a genuine permission/resource gate and continue independent work if repair cannot proceed.

Before declaring a required secret missing, check the configured credential sources (including Bitwarden and its session in Credential Store, where configured), using supported tools; install the official client only if authorized. Never export a vault, expose secrets, or create persistent access to work around a gate.

On a supervisor next-step handoff, read any new or revised Product Owner guidance first; record the consumed comment/revision and acknowledgment in private task notes without refreshing Last updated. Check it against current evidence and permissions, resume the permitted stage, and link the resulting artifact. An unchanged task count/status never cancels this handoff: compare the candidate SHA, run/attempt, failure cause, owner acknowledgment and artifact movement. Reuse the existing repair or owner; deduplicate reminders, not authorized recovery, and follow the bounded recovery rules rather than repeating identical messages. `Open` means not being worked now — the row text carries the concrete next step and what starts it; it is not proof of execution, approval, resolved gates or completion, and promises no specific start time. If the step still cannot run, return fresh failure evidence and the smallest decision needed; never repeat the old blocker without checking it. Keep one owner; escalate rather than silently abandoning the handoff. Existing permission, release, review and validation gates still apply.

## Stage 3 — Implementation (implementation subagent)

The task subagent spawns an implementation subagent. Brief points at: the issue, the Notion design/PRD, the acceptance criteria. It works in a branch, opens a PR linking the issue, reports the diff summary + its own local test evidence. It does NOT merge.

## Stage 4 — Review loop (review subagent)

1. The task subagent spawns a review subagent. It first reads the Notion design/PRD + acceptance criteria, then reviews the PR against them: diff actually read, evidence claims checked, criteria tested one by one.
2. Findings → implementation subagent fixes → re-review. **Loop until clean.** No "good enough" exits.
3. Anomaly rule (task subagent watches): two rounds bouncing with substantive findings = structural problem (bad design, wrong scope, misunderstood ticket). Stop, diagnose, fix the design or the brief, restart.
4. Evidence runs in a REAL git checkout, never a tarball tree (lesson 2026-10-31, PR #5757: a tarball silently fails ~39 git-dependent tests). Suite can't complete (hangs, tooling gaps) → bounded head-vs-base comparisons on identical trees; report the hang itself.
5. **Test-count delta line (audit 2026-11-05):** every Stage 4 verdict records the PR's test delta — new test cases added / cases removed / test-file count before→after. Net growth with no recorded exception on the issue fails the review: the standing rule is no growth; AC-mapped cases for genuinely new behavior are the only exception, and the exception is written on the issue, never assumed. (Audit found 5 merged PRs — platform #308/#310/#311/#314, VWA #2330 — that quietly added cases with no exception recorded.)

## Stage 5 — Merge (task subagent)

1. Review clean → CI on the PR head → green → merge. Verify the merge by SHA readback. Post the merge comment. The issue does NOT close here — it closes at Stage 6.
   **Gate order (weekly review, 2026-10-31):** "review is clean" = the verdict comment EXISTS on the PR and the task subagent has read it back via API (comment id + head SHA it names). A subagent's delivered PASS is not the gate — PR #5782 was merged at 10:59:50Z on a delivered PASS whose verdict comment landed 11:01:53Z. Read the verdict back first, then merge.
2. **CI infrastructure unavailable / checks failed:** diagnose and repair the infrastructure while continuing independent work. A check that ran and failed blocks the merge — UNLESS a triage recorded on the PR proves, with run IDs, that the identical failure occurs on main or is fleet-caused AND could not have been caused by this change; an untriaged failure, or one the change could have caused, is never bypassed. Checks that never ran (CI globally unavailable) may use the local-evidence ladder: run the full relevant suite on the exact SHA, merge on local evidence, and record the bypass + reason on the issue for re-verification when CI recovers — only when the current project rules and user explicitly authorize that exact path, preserving review and merge gates. Queue delays alone grant no exception. Otherwise keep the merge held while repairing.

## Stage 5.5 — Design/PRD sync check (after every merge, Den 2026-11-01)

A merged fix can silently make the Notion Design or PRD wrong. Before Stage 6 closes the task, the task subagent checks both, every time:

1. **Design:** does the merged change alter anything the task's Design doc (or a standing design page — Testing & Release Process, Autoscaling, DESIGN) describes — behavior, contracts, invariants, alert/verdict semantics, workflow rules, file/test inventory? Yes → update the doc in the same task (per `dev_docs`: concrete nouns/numbers), read it back, link the update on the issue.
2. **PRD:** does the merged change alter anything the PRD promises — product behavior, user-visible flows, pricing/entitlement mechanics, supported surfaces? Yes → update the PRD the same way. (Internal CI/tooling fixes almost never touch the PRD — but the check is still run and recorded, not assumed.)
3. **Record the outcome on the issue either way:** "Design/PRD sync: Design updated <link> / PRD updated <link>" or "Design/PRD sync: checked — no update needed", with the one-line reason. A task whose sync outcome is not recorded is not closed.
4. The investigation track's design-repair-before-fix (step 2) does NOT replace this check: the pre-fix repair covers the gap that caused the bug; the post-merge check covers everything else the fix changed that the docs describe.

   *Tooling note (2026-11-01, hit on #5804 and #5819):* Notion `update_content` replaces match the page's markdown, not the fetched rendering — anchor on plain-text phrases; a backticked/code-spanned old_str can no-match even when the rendered text looks identical. Verify every sync edit by re-fetch before recording it.

## Stage 6 — Post-merge validation (validation subagent)

Immediately after the merge, the task subagent spawns a validation subagent — never the implementer. It checks the merged result on main: the changed flow works end to end in a real environment (real product flow or live service, per the testing rule), and nothing around it broke (adjacent flows). Validation must also re-run the acceptance criteria against relevant account/tier/state variants absent from the committed test fixtures — fixtures encode the happy class only (lesson 2026-11-01, #2154: the committed AC-6 fixture was a free-tier account; the paid-tier retry class carried a live bug — Play-gate misclassification after subscription cancel — that two review rounds and the committed suite all missed and Stage 6 caught). Evidence goes on the issue + the Work Log row, in a comment explicitly labeled **"Stage 6"** (audit 2026-11-05: VWA #2315's validation existed in substance but unlabeled, and #2323 was closed on its merge comment with no Stage 5.5/6 records at all — unlabeled evidence is unauditable evidence). The closing comment also repeats the test-count delta line. Failure reopens the relevant stage; the task is not done. **The issue closes and the Work Log row goes Done ONLY when validation passes AND the Stage 5.5 Design/PRD sync outcome is recorded on the issue. Never close on the merge comment alone.**

**Deploy is not part of this workflow (Den, 2026-11-07 — the deploy step is removed from the protocol).** A task ends at Stage 6: merge SHA read back + Stage 5.5 sync recorded + Stage 6 validation passed on the merged result = Done, issue closed, row Done. Whether and when merged work ships to production is the product owner's separate release act, outside any task's lifecycle; it never keeps a task open and is never a residual class. Release-level live checks belong to the release task itself, not to the work tasks whose merges it ships.

## Standing rules

- **Testing rule (Den, 2026-10-31; also in the Notion DESIGN page + Testing & Release Process page):** no unit tests, no mock-based tests. A test runs the real product flow end to end (PRD journeys, payment flows) or live against real services. **Do not grow the test count.** Missing coverage → extend an existing integration/e2e test, never a new file. A PR adding a unit or mock-based test fails Stage 4 on that ground alone. (Record: mock mass cut 978 → 79 files, 2026-10-31, PR #5786, issue #5780 — the mock suites passed while production broke.)
- **Customer/tenant/Stripe facts come from the Admin API.** How-to: AgentPod repo `docs/admin.md` + `.agents/skills/admin-console/SKILL.md` (auth via the Notion "🔑 Admin Access" page). Any investigation touching customers, payments, or tenant state routes through it; "behind the console, unverifiable" is not a verdict until that route was tried.
- **Verify live, never from document audits alone.** "Unverified" is a hypothesis, not a finding. A stage counts only with its artifact: Notion page updated, PR open, verdict recorded, merge SHA read back.
- **Sweeps close, never delete (audit 2026-11-05).** A backlog sweep closes or archives issues; it never deletes an issue that has a merged PR or any pipeline record — deletion destroys the audit trail (the 2026-11-01 sweep deleted VWA #2320, leaving PR #2316's Stage 5.5/6 permanently unverifiable).
- **Runner/CI claims are per-lane, per-run facts (weekly review 2026-11-02; Den's correction 2026-11-01 14:04 UTC).** Before citing a runner blocker, read back the exact workflow run's jobs: runner name, requested labels, state. Failed checks ≠ no runner; queued/unassigned ≠ fleet offline. Lanes differ per repo — platform PR #300 checks executed on agentpod-ci-v153-d while VWA `vibe-shared-ci` jobs sat queued/unassigned. The blanket "platform 0 runners / VWA runner offline" claim parked work on a false gate until Den corrected it; never reuse a runner diagnosis without refreshing it.
- **Subagent reports are not evidence (weekly review, 2026-10-31).** A subagent reported PR #5780 with SHAs and test counts and two reviewers "verified" it — the PR never existed (newest was #5775); another reported its ticket as #5781 when it was #5779. Rule: the task subagent reads back EVERY stage-reported identifier before acting; the main session does the same when reconciling or reporting to Den. Read each identifier (PR/issue number, head SHA, merge SHA, comment) from the GitHub API before acting or reporting to Den; implementation briefs require the subagent to cite API readbacks, not assertions. A number that 404s is reported as unverified, never passed on. Issues and PRs share one number space (lesson 2026-11-01, #5806/#5817): a brief's "fix issue #N" may be PR #N — verify the object type via the API before treating it as an issue, and say which it is in the claim comment.
- **A stage agent that ends without a report may still have done the work (lesson 2026-11-01, #2154).** Twice in one task an agent died mid-run (one after pushing its fix commits, one on a daemon restart before posting its verdict). Before re-dispatching the stage, check the state it may have left: branch heads vs the last verified SHA, PR comments, evidence files on disk. Re-dispatch only the missing remainder — never restart the stage blind (a blind restart risks duplicate verdicts and double pushes).
- **Tooling hygiene:** when refreshing a single-line record in Notion (e.g. the Agents Context escalation line), replace the FULL old line and read back that exactly one such line exists — a prefix-only replace leaves the old body appended (hit twice, 2026-11-01/02 Supervisor runs). Durable helper scripts live under `~/workspace/`, never `/tmp` (wiped without notice; a GitHub helper was lost mid-session, 2026-10-31). Parallel API calls write to separate output files — two calls sharing one file corrupt both reads. A half-finished API reconstruction left in a workdir carries a state note (base commit + tree SHA, blobs fetched/total, the resume command) — the #5819 takeover recovered the prior attempt only because `fetch.log` + `resume_fetch.py` happened to exist; the next one should not depend on luck.
- Report outcomes to Den, not stage narration. Surface mid-flight only for a genuine blocker you cannot resolve yourself, with what you already tried.
- Non-financial decisions inside a ticket are the main session's — decide and record. Financial impact or Den's credentials/time go back to him.
- **Decision reversal (lesson 2026-10-31, #3271):** when Den reverses a decision recorded on issues/PRs, execute it the same turn, before work on the new direction: post a supersession comment (old decision + new one) on EVERY issue/PR that recorded the old one — duplicates included (#3271's closure also sat on #3334) — and reopen any issue the old decision closed. A stale closed record misleads the next actor.
- **Decision asks present the full menu (lesson 2026-10-31, #3271):** an ask to Den names every disposition the record supports — for money owed: refund / deliver the service / credit / write off — never a single preselected approve/deny. (The refund-only framing reached Den first; his choice, deliver the service, wasn't in it.)
- Never print secret values anywhere (issues, Notion, chat, logs).
- **Local-evidence environment (lessons from #5288, #5803, 2026-10-31):** (a) Exec backends share no system state — apt installs and `/tmp` vanish between calls; `~/workspace` persists. Local Postgres: `apt-get download` the .debs, `dpkg -x` under `~/workspace`, copy to `/tmp`, throwaway user, `initdb`/`pg_ctl` as that user (root is refused; a dropped uid cannot traverse `/home/hatch`); run suites promptly in the same stretch of calls. (b) A backgrounded run reporting exit 0 with empty output is NOT evidence — capture output to a workspace file, cite the summary lines. (c) Subprocess-heavy invariant suites time out under parallel batch load on this VM — run them standalone. (d) Before pushing, diff every touched file against CURRENT main blobs — a stale-base tree silently reverts fresh merges (nearly reverted #5763's ci.yml block); main can move mid-task, so re-read the head SHA immediately before pushing. (e) Test fakes encode contracts: when a fix tightens a consumer to the producer's real shape, update the fake to the real shape and say so in the PR — fixture correction, not test weakening. (f) Reconstructed checkout when clone is blocked: build the tree from the Git Database API (recursive tree + blobs), `git init`, force-add gitignored-but-tracked files (`.env.example`, stray `package-lock.json`), restore symlink modes — valid ONLY when local `git write-tree` equals the API tree SHA of the base commit; if main moved, re-base the changed blobs onto the new tree and re-run the gate on the final tree before the PR. Subtree variant (hit 2026-10-31, #5826): when only the test-relevant surface is content-fetched and the remaining blobs are index-registered by cacheinfo only, git ≥2.43 needs `git write-tree --missing-ok` — valid only paired with per-file sha1 verification of every fetched blob and an API-side check that the created PR tree equals the local final tree. (g) Never `git add -A -f` in a reconstructed checkout AFTER `npm ci` — `-f` overrides .gitignore and stages all of node_modules (hit 2026-11-01, handoff extraction PR #2323): stage before installing, or stage changed files via plumbing (`git read-tree <base-tree>` + `hash-object`/`update-index --cacheinfo` per file) and let the write-tree gate prove the index. (h) Fetch economy (hit 2026-11-01, #5844): blob fetches for a reconstructed checkout go serially (≤4 workers max, and even 4 hit write EPERMs — serial is the reliable default) — a 16-way parallel fetch tripped a secondary rate-limit cooldown on the shared token that outlasted the hourly reset; `/rate_limit` readings flip between surrogate credential pools and are not evidence — a real repo call returning 200 is.

## Improving the process (standing duty)

Fold every friction lesson (dropped stages, stale boards, colliding claims, repeating review findings) into this skill at reflection time, before reporting the task done — reflection + skill update closes every task. Keep the pull script honest: if its linking misses a shape (PR references its issue only in a commit message), fix the script and note it here.

Stall pattern #1 (2026-10-31): Stage 4 reviews for smaller PRs (#5765, #5773) sat undispatched while larger items absorbed attention — sweep for un-reviewed PRs at every status request.

Stall pattern #2 (weekly review, 2026-10-31): **merged-but-open issues** (#5722, #5678, #5766: fix merged, issue open on residuals). A merge comment lists every residual and classifies it — fleet / Den-gate / follow-up ticket (with number) — or the issue reads as done when it is not. ## Hourly job self-improvement

**Roles.** Each project has ONE hourly cron, the **Supervisor**, running the protocol in **Dev Workflow Supervisor** (`~/workspace/custom-skills/dev-workflow-supervisor/SKILL.md`) — one template over this skill, instantiated per project (`agentpod-hourly`, `vibebrowser-hourly`, `homesteadlink-hourly`, `opencode-hourly`) and differing only in project parameters: Work Log, PRD, Design, Decision Log, repos/pull script, project constraints. The Supervisor scans the Work Log, diagnoses, dispatches, verifies receipts (merge SHA read back, issue closed, deliverable at its recorded path), reflects, and self-edits. It never implements code or runs task stages itself. The Supervisor dispatches one **task subagent** running **dev-workflow** (`~/workspace/custom-skills/dev-workflow/SKILL.md`): it owns one task end-to-end (Stages 0–6) and reports its receipt back. A task with no live task subagent requires diagnosis, claim checks and an actionable next stage before re-dispatch; a live task subagent that went quiet is steered, never duplicated. The **Overflow** skill (`~/workspace/custom-skills/overflow/SKILL.md`) is that task subagent's legacy alias.

**Self-improvement — the final step of every Supervisor run:**

1. Scan the project's Work Log rows and the job's recent runs for REPEATED failure patterns — the same kind of stall, misdiagnosis, wasted check, or wrong stage recurring across tasks/runs. Find where the agent keeps going wrong across the list, and fix that recurring cause in the job's own instructions. One-off incidents are logged, never edited for.
2. If scheduler self-editing is authorized and supported, apply the concrete fix to this job through its actual scheduler tool (for example `cron.update` where available); otherwise record the proposed fix and missing capability/approval, without claiming it was applied. Hard limits: schedule, delivery chat, owner, enabled state, and the verified project parameters (Work Log / PRD / Design / Decision Log links) remain byte-identical; only the loop's working instructions change; a self-edit never expands the job's authority (no new permissions, release actions, chats, or projects).
3. Every self-edit is recorded in the same run: one line in the job's own session chat ("self-edit: <what changed> — <why>"), even when the run otherwise reports nothing, plus a dated entry with the same content in the daily log (`~/memory/YYYY-MM-DD.md`). No silent self-modification.
4. A lesson that applies to all projects is appended to this skill as a lessons/reflection entry (see "Improving the process") — never as a rewrite of the core protocol.

Properties, in order: **Title** · **Last updated** (date with time; default view sorts by it descending, stalest at the bottom) · **Description** (one-two lines: what it is + the exact gate) · **Status** (exactly five values: `Open` / `In progress` / `Blocked` / `Done` / `Closed`; the Supervisor works Open rows in priority order — highest project priority first, oldest first within equal priority) · **Owner** (multi-select agent name; select one owning agent) · **Owner session ID** (text; the actual owning task session ID) · **Links** (GitHub issue URL + PR URL) · **Doc** (Notion design/doc URL).

**Status vocabulary.** Statuses are exactly five — `Open` / `In progress` / `Blocked` / `Done` / `Closed` — defined once in `dev-workflow-supervisor` (**Read first**). A completed task is Done, never Closed; Closed means closed without being done.

### Ownership fields

- `Owner` names the agent responsible for the task (use the existing option, such as Muse, Codex or Hermes), not a human assignee or the model used for one stage. `Owner session ID` is the owning task session's exact runtime identifier, verified from the runtime or an explicit claim and linked to that evidence in the notes; it never appears in public issue or PR comments — public claims carry the agent name/role only. A self-reported claim does not prove the session is still live.
- `Worklog ID`, when present, is Notion's generated row identifier. Never copy it, an issue number, a model name or a guessed identifier into `Owner session ID`. If the actual session ID is unavailable, leave that field blank, record why, and resolve ownership before a new dispatch; do not erase an existing verified owner.
- Keep stage-subagent IDs and the main Supervisor session in notes under their roles. They never replace the owning task session. Preserve both ownership fields while a task waits or completes; transfer them only after checking the prior owner has stopped or explicitly handed over, recording the old owner and transfer evidence.
- On claim/resume, fresh-read the row and competing claims, write and read back both ownership fields, then record execution evidence. A review-only comment does not acquire ownership. Backfill only explicit, unambiguous ownership evidence; do not adopt a stale claim as a live session.

Rules:
- A row goes **Done only with Stage 6 PASS recorded on its issue** — a merge alone never makes a row Done (weekly review, 2026-11-02: #5851 was marked Done on merge, a Product Owner review revoked it to deploy-proof Unblocked; prod was never validated).
- Row created **when work starts** — the same moment it is claimed/dispatched (Starting a task, step 2).
- Update the row at each execution milestone: claim acknowledged → design → PR opened → review → merge → validation → execution block → done. Set **Last updated** to the actual evidenced execution/progress time, including verified artifact movement discovered later, not the time of the scan. Refresh Description when the gate changes. Review-only guidance, schema edits, ownership backfills and Blocked → Open relabeling must not advance Last updated; date those observations in the comment instead. Keep artifact URL/SHA and movement time in notes; do not invent a date for unknown progress.
- `Open` = not being worked now; the row text carries the concrete next step and what starts it. A Blocked row whose reason has cleared is worked the same run (see `dev-workflow-supervisor`), not merely relabeled; keep unresolved reasons explicit. The main session sends the handoff through the actual task-subagent tool. Move to In progress only after acknowledgment and evidence that execution started or resumed, not a comment or dispatch receipt.
- Blocked rows name the exact unblock in Description (whose decision, what input, which host). "Blocked" without the unblock is a stall, not a state.
- Every board report reconciles GitHub (pull script) against the Work Log: a row whose GitHub state moved is updated in the same turn; a Done row is verified against GitHub before it is repeated as done.
- **Staleness rule:** no artifact movement **>2h** is a stall candidate, even if Last updated changed. Inspect the live owner/session and fresh gate evidence; steer a live owner, or transfer a stopped owner’s claim before re-dispatching actionable work. Follow `dev-workflow-supervisor`; comments and status edits do not reset the progress clock.
- The hourly per-project Supervisor crons sweep on this rule between board reports; they never replace the in-turn duty to keep rows current.
