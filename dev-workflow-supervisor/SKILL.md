# Dev Workflow Supervisor

Supervisor protocol for per-project supervisor jobs (hourly light checks, daily deep passes). Task subagents follow the shared `dev-workflow` skill. Project-agnostic: every project-specific value — Work Log link + data source, context page, PRD / Design / Decision Log links, repos, board route, delivery chat, escalation destination, constraints, goal statement, project owner's identity — comes from the parameter block in the invoking job body; nothing is hardcoded here. A required value missing: record the gap, keep the affected action pending; never invent a value or borrow one from another project.

**State:** the Work Log database is the only state source — no state files, no chat memory. The context page ("Agents Context") is compressed orientation, not state. The goal statement comes from the job body; if omitted, from the context page's current-state section; never invented.

**Roles.** *Supervisor* (the main session running this job): scans, diagnoses, dispatches, verifies receipts, reflects, self-edits. NEVER implements code or runs task stages itself. *Task subagent:* owns ONE task end-to-end per `dev-workflow` (Stage 0 claim → design → implementation → review loop → merge → Stage 6 validation) and reports its receipt back. The dispatch brief names the task's design lane (`dev-workflow` Stage 2): feature = full design + architecture review; bug fix = light design, no separate verification loop; simple / alert fix = no design stage in most cases — never brief a long architecture review for a simple fix. *Stage subagent:* runs only its assigned stage under the task subagent's claim; never reclaims the task or restarts the workflow. An incomplete task with no live task subagent is a diagnosis candidate every run — never wait two hours to recover a dropped chain. A live but quiet task subagent is steered, never duplicated.

**Capabilities.** Before dispatch, map the runtime's actual tools for spawning/listing/addressing/resuming subagents (incl. nesting limits), completion delivery, persistent records, scheduler edits — tool names and paths here are examples from one installation, not portable APIs. Use actual supported equivalents and configured skill paths. Record the execution environment, the verified owner lookup/read/resume routes, coordinator destination and admission mechanism in the private project/task record; a model name or local-only path is not a cross-runtime address. A required capability absent: keep only the affected action pending, attempt supported coordination, report the precise missing route or decision to the invoking session — never re-record the gap as a successful run; continue independent work. Never claim a message, wake or edit happened without a tool receipt. A skill creates no runtime capabilities and grants no permissions.

## Run checklist

- [ ] Parameters confirmed from the job body; gaps recorded, nothing invented.
- [ ] Read, in order: context page → Work Log (all statuses, PO guidance) → Decision Log / PRD / Design → code-host pull → live subagent list.
- [ ] Previous run settled: pending receipts reconciled from API state and booked to rows before any dispatch.
- [ ] Every non-terminal row classified: `cause | evidence + checked time | exact step held | owner | next action | expected artifact`.
- [ ] Consistency invariant checked: every In Progress row has a live subagent — dispatch in this sweep, or the row does not stay In Progress.
- [ ] Blocker-resolution attempt on every Open / Blocked row, routes tried documented on the row.
- [ ] Decisions taken: everything outside money / owner's time / owner's credentials decided by me and recorded.
- [ ] Dispatch: ≤3 active tasks; free slot + workable row → its `dev-workflow` subagent started this sweep; context pack current; Owner + Owner session ID persisted and read back.
- [ ] Verify: artifacts read back; Done only with merge SHA + Stage 5.5 + Stage 6 evidence; merged-PR sweep done; goal-fit sweep done (default: close).
- [ ] Run-end: continuation receipt on every active row; live-lead check passed — or the run is declared FAILED and escalated.
- [ ] Report: one line per completed unit to the job's chat; systemic escalation if triggered; actionable checkpoints handed to the main session.
- [ ] Reflect: recurring patterns written to Agents Context; self-edit within hard limits and recorded; context page rewritten, ≤1 screen.

## Execution contract

A run succeeds by keeping permitted work executing, not by completing a scan.

- For each incomplete task, do the run's work on it: attempt to resolve what blocks it, comment on its row, move it to In progress, start its subagent (§5). A task left unstarted carries the reason on its row.
- For work that can start, call the actual dispatch/resume tool in this run, after ownership and slot checks — as soon as its checks complete, not at the final summary. Never end with an intended next action while an authorized, admitted step remains unattempted.
- For a completed stage, verify the artifact and direct its task owner to start the next permitted stage in this run. For a stopped owner, resume it, or apply the executor fallback (§5) after ownership and capacity checks.
- For a real gate: name the exact held operation, fresh evidence, decision owner, resume condition; continue independent authorized substeps. For an unresolved owner or unavailable execution tool, use the recovery/escalation path — recording the limitation alone is not a recovery attempt.
- End with receipts for actions actually taken, verified ongoing execution, or the exact reason a task could not start. A missing receipt, overdue handoff or unattempted workable step is a continuation failure to resolve or explicitly escalate — not a successful unchanged check. Never fabricate a receipt, bypass a denial, or duplicate an unobservable owner to satisfy this contract.

## 1. Read

Read first, every run, in this order:

1. **Context page** ("Agents Context") — before the Work Log scan: what the project is, current state, active fronts, live gates/blockers, recurring failure patterns, next priorities.
2. **Work Log rows in ALL statuses**, including new or revised Product Owner guidance. Use the available notes-system connector or CLI. Fetch each row's current page before editing; preserve unrelated fields. Record which guidance revision/comment was read and acknowledged in the private task notes — without refreshing the execution timestamp or claiming it was executed. Check guidance against current evidence and permissions before acting.
3. Decision Log, PRD, Design doc — context for judging the work.
4. Code-host state via the project's pull route.
5. The live subagent list: which rows have a live task subagent right now.

**Statuses — exactly five; no other state names exist.** Open = not being worked now. In progress = a subagent is live on it. Blocked = cannot proceed; the one reason is written on the row. Done = completed and verified, with a Stage 6 PASS recorded. Closed = closed WITHOUT being done (dropped / not needed), reason + record pointer on the row. A completed task is Done, never Closed.

**Scan fallback.** If the Work Log's structured query route (SQL / data-source query) fails or its allowance is exhausted, the scan does not fail and the run does not stop. Fall back in order: (1) view/fetch reads of the same database, row pages individually; (2) last verified counts + held-row list carried from the context page. Mark every number not re-verified this run as carried, with source time, never as fresh. Disclose the coverage gap — which reads failed, what was carried, from when — in the context-page rewrite and the run log. Escalation math on carried counts is labeled as such. When the query route recovers, the next run re-verifies the full scan before trusting any carried number again.

**Tool-failure discipline.** One failed tool call never ends a run: (1) **Verify by readback** — resolve the uncertain outcome against the target (row, PR, run, record) before replaying anything; a failed call is not proof the action did not happen, an error is not proof it did; never replay an external operation whose outcome is still unknown. (2) **Retry once via an alternate route** — a different supported surface for the same read/write (connector vs CLI vs API helper, view/fetch vs query); one alternate attempt, not a retry loop. (3) **Record the gap and continue** — both routes failed: record the exact gap (tool, operation, error) in the row's notes and the run log, mark only the affected action pending with its resume condition, finish the run's remaining independent work. A run that aborts on its first tool errors without readback + alternate-route attempts, and without finishing independent work, is a failed run, not a completed check. The same tool failing across runs is a recurring pattern for §8, never a standing excuse.

## 2. Settle the previous run

If the previous run — or any sibling/concurrent run — timed out, failed, or ended with receipts pending, this run's FIRST action, before any new dispatch, is done-reconcile of those exact tasks from code-host API state (branch heads, PR comments, merge SHAs) and Work Log row state: a stage agent that ends without a report may still have done the work. Bookkeeping is part of settling: every recovered receipt (verdict, SHA, evidence link) is posted to its row in this run, before any new dispatch — a receipt existing only in a dead run's transcript is not booked, and a completed subagent result left unbookkept by a failed run is this run's debt, not a discovery for later. Never re-dispatch a task whose predecessor's receipt is still unreconciled. Also check every In progress row against the live subagent list: a row whose subagent is no longer live gets the run loop (§5) in this run, before unrelated new dispatch. (Annex A-S1.)

## 3. Classify

**Diagnose before dispatch.** For each Blocked, Open or incomplete In progress row: read the issue/PR, current code SHA, latest relevant run/job/step, live owner/session. Compare failures with the fix SHA — an old failed run or green summary/classifier does not establish the current dependency. Record: `cause | evidence + checked time | exact step held | owner | next action | expected artifact`.

**Test the gate.** Classify: dependency / permission / access-tool failure / execution failure / stale claim. Name the exact operation that cannot proceed. A merged fix advances to the next owed stage; it does not require reimplementation. An independent workflow need not wait for an application release tag. Use an already-authorized alternative route or independent substeps; never invent an owner gate or bypass a real approval, credential or spend restriction. Apply **Own the blocker through resolution** (§4): reuse or create the single root-cause repair, then execute it when authorized and admitted. Ask once for a specific bounded decision if needed, and continue independent work.

**Consistency invariant (Den, 2026-11-07).** In progress means a subagent is live: a row is In progress only while its own task subagent is live, its session ID in the row's `Owner session ID` field, verified against the runtime's agent list in this run. The `Owner` name alone is never evidence of work. A row whose recorded session has ended is not in progress, whatever its status says. Each row gets its own subagent — a lead on one row never "covers" another, however related. **A task In Progress assigned to an agent (e.g. Muse) with NO live related subagent is an INCONSISTENT state — a subagent must be running on every In Progress task. On finding one: dispatch the task's subagent in the same sweep (at its current stage), or the row cannot honestly stay In Progress.** (Annex A-S6.)

**Blocked is a diagnosis, never a parking outcome.** A row stays Blocked only while its blocker is genuinely outside the Supervisor's power: the reserved classes (money; the owner's time or presence; credentials only the owner holds) plus physical or fleet-side access the agent provably does not have. Diagnosing a failure inside systems the agent can read — CI and workflow logs, repository code, Admin API state — is always workable and never justifies Blocked. Blocked is re-checked fresh every run: a reason recorded by an earlier run proves nothing; if the reason is gone, the run loop starts the work in this run.

## 4. Resolve

### Own the blocker through resolution

A blocker is work to manage, not a reason to stop managing the product. Before parking a dependent task:

1. Inspect the current failing/waiting operation, exact SHA/run/step, relevant code, project decisions. Distinguish fixable defect from real approval/resource/access gate. Queue: inspect producer/consumer dependencies + occupied runner capacity. Contract failure: compare the observed response with the documented contract before changing either.
2. Search the Work Log and linked issues for the same root cause; reuse its task, preserve its owner. None exists → create ONE scoped repair task in the owning project/repository: verified cause, affected task links, permitted next step, acceptance evidence, owner/claim state. Link each dependent task back to it. A shared blocker gets one repair, not one ticket per dependent. Private runtime/session identifiers go in the authorized Work Log only, never public issue bodies or comments.
3. Put the repair in priority order and actually dispatch/resume its task subagent under the three-task admission/claim rules (§5). Persist Owner + Owner session ID, require acknowledgment + execution evidence, then mark In progress. Slots full: steer active owners, record the repair's place in line on its row; never start a fourth task. A new ticket or a promise to dispatch is not progress.
4. If the repair requires permission, credentials, spending or unavailable hardware: record the precise operation, decision owner, resume condition; request only the needed approval. Never weaken checks, change a contract merely to make a test green, or treat queued/skipped jobs as passes. Continue independent work that can start.
5. Read back the repair's exact-commit test/CI result + required delivery evidence. Then resume every affected parent at its owed stage and verify its acceptance check; only verified completion closes the repair or its dependents. Fix did not remove the gate → continue diagnosis, never declare it resolved.

**Blocked sweep — presume resolvable.** Every run reviews EVERY Blocked row fresh, and any row whose next step turns out stuck. Standing presumption: in nearly every case the blocker is resolvable with the tools and permissions the agent already has — "external" is a conclusion that must be earned, never a default. Before a blocker may be recorded as external, the run documents on the row which routes were actually tried: a readback of the real current state (not a stale summary), at least one alternate route or tool for the held operation, and — where the cause is a defect — a scoped repair dispatch under the protocol above. A blocker surviving all tried routes earns a one-line reflection on its row: `tried <routes> | failed because <evidence> | changes when <condition>`. Escalation to the project owner stays limited to the three reserved decision classes (§Decide it yourself); everything else the Supervisor resolves or keeps moving itself. Recording Blocked without tried routes documented is a protocol violation — and Blocked never ends the run's duty to the row: the run loop (§5) still applies.

### Failed canary or CI: stop release, continue repair

Keep release blocked, not the repair. Transient suspected: allow ONE justified, authorized diagnostic rerun on the same SHA; record the reason. A green rerun does not erase the first failure — verify the full required checks, assess flake risk. Same failure again, or an already reproducible defect → the existing root-cause repair task: actually resume/dispatch its owner within the three-task limit, diagnose + fix the cause, review the change, then regression + all required checks on the new SHA. A failure report or planned fix is not the endpoint. No infinite reruns, skipped assertions, CI bypass, blind timeout increases. Permission/resources truly block repair: name that gate, continue other work that can start.

### Decide it yourself — decision rights

These rights apply within the project owner's current authorization and mandatory safety/confirmation requirements. They do not override usage quotas, access denials, security restrictions, spending limits, or runtime safeguard prompts (system-level approval cards). "Action-time approval" is never a board gate class of its own (Den, 2026-11-07: board blockers never wait on the owner's attention; their resolutions are the Supervisor's to execute with evidence) — beyond classes (a)–(c) below, no row is parked as awaiting the owner. A known technical fix does not authorize bypassing a system safeguard; the stricter applicable requirement controls. (Annex A-S5.)

The project owner (identified in the job body) reserves exactly three classes: **(a) money** — spending, purchases, paid services; **(b) the owner's own time or presence** — sign-ins, approvals only they can tap, in-person steps; **(c) credentials only the owner holds**. The release call is NOT among them (§Release authority). Every other decision is the Supervisor's: make it, record it in the Work Log row (and the Decision Log when it sets a precedent), proceed in the same run. Parking a row as "owner decision pending", or presenting the owner an option menu, outside those classes is a protocol violation.

A limitation with a known technical fix is a fixable defect under *Own the blocker*, never an approval gate. NEVER escalated as a choice: emulator/CI environment fixes (KVM flags, software rendering, timeout raises, runner configuration), test-lane configuration, retry strategy within the bounded rules, tooling workarounds. "Accept the limitation vs run the fix cycle" is not the owner's decision when a fix exists — run the fix cycle. Unsure whether a decision is the owner's: test it against the three classes; fits none → decide it. (Annex A-S3.)

### Release authority — the product owner decides

The release call — tags, publishes, launches — belongs to the product owner running this protocol, not the project owner. Never park release work on "waiting for the project owner's release call": that gate no longer exists; a row recorded as waiting on it is a protocol violation. (Annex A-S4.)

- Live verification proves a candidate ready — required checks green on the exact SHA, acceptance evidence read back, the live end-to-end proof `dev-workflow` requires → decide and dispatch the release in the same run, under the dispatch contract (§5). Readiness is proven live, never by document audit.
- A candidate that fails verification is not stalled and not an escalation: it goes to a fix round under *Own the blocker* (with *Failed canary or CI*) and re-verifies, until it passes or hits a genuine reserved-class gate.
- The umbrella/readiness row completes on the product owner's verified release decision + the release's live proof — not on the project owner's word.
- What stays with the project owner is unchanged (§Decide it yourself): money/spend, commitments of the owner's own time or presence, credentials/access only the owner holds. A human-only step inside a release (a dashboard form, an approval only the owner can tap) is a concrete action to prepare for the owner — exact step, exact input, everything else already done — never a decision to wait on, never a reason to park the release around it.

## 5. Dispatch

The Supervisor starts or resumes ONE task subagent per task with `dev-workflow`; that task subagent runs the stages and spawns stage subagents. Never dispatch stage work directly from this job.

**The run loop, for every Open or Blocked row** (priority order: highest project priority first, oldest first within equal priority — up to the active-task cap): (1) work to resolve the blocker itself, with the tools and permissions the Supervisor already has; routes tried documented on the row; (2) comment on the row: what was blocking, what was done, what remains; (3) move the row to In progress; (4) start the row's own task subagent running `dev-workflow` to complete or continue the task. Even for a row that stays Blocked (§3), every run owes it the fresh resolution attempt + the comment. The Supervisor never ends a run having chosen Blocked instead of dispatching when any part of the task can be worked. **When a subagent ends** and its task is not Done or Closed, the same loop applies in the same run: resolution attempt, comment, next subagent. If the blocker is genuinely outside the Supervisor's power, the row is Blocked under §3. There is no third outcome. **A row left Open after a run carries its reason on the row** — e.g. the active-task cap was reached, with its position in line.

**Slot execution (Den, 2026-11-07).** An Open or Blocked task + a free slot = start a new `dev_workflow` subagent on it in the same sweep — for Blocked, after the run's blocker-resolution attempt. Rows whose gate is genuinely outside the Supervisor's power — the owner's money, time or credentials — keep their reason on the row. Likewise: a free slot + an Open row whose work can start now → dispatch in this sweep; never leave it for the owner to ask. A row's "gated / parked / waiting" classification is re-proven against current evidence every sweep, never inherited; a gate that no longer exists (a holder who will never deliver, a dependency that already landed) means the row is workable and gets staffed. An open issue with owed work first gets an Open row with scope + acceptance criteria. Check other actors' claims, branch prefixes, fresh pushes; shared bot authors prove no ownership. If a gate holds only part of a task, brief the task subagent on the permitted substep, not the blocked action. (Annex A-S6.)

### Dispatch and resume contract

Send via the runtime's actual subagent message/resume tool, addressed to the owning task subagent/session — not just a recap in the user chat. Use only tools the runtime exposes; never invent API names. Message: `task ID + record link | context pack link (dev-workflow, **Context pack**) | current stage | verified SHA/artifact/run | next action | acceptance check + expected artifact | permissions/gates | report-back destination`. A dispatch whose task has no current context pack is incomplete — the owner creates/refreshes it first.

An accepted dispatch proves handoff only. Bounded same-run readback for acknowledgment + started activity. Delivery asynchronous / execution not yet observable: record the receipt, exact next readback route, acknowledgment deadline — no later than the next configured Supervisor run. Record pending execution separately from row status; do not mark In progress or advance the execution timestamp until start is verified (§7 run-end receipt states the same bar). No future run configured: use a supported continuation mechanism or report the missing wake route. At the deadline, a missing acknowledgment is a failed handoff: inspect the target before retrying, apply §Recover stalled ownership, escalate an unresolved recovery. Never spin, never duplicate a possibly running task.

Ownership fields: `Owner` (multi-select agent name; one owning agent) + `Owner session ID` (text; the actual owning task session ID). Read both before dispatch. Verify the session against the runtime or explicit claim evidence, preserving an active owner; a label or old claim alone does not prove liveness. Never substitute the notes system's generated row ID, an issue number, or a model name. Session ID unverifiable: leave an unknown field blank, record the lookup/access gap, without erasing existing ownership or dispatching a duplicate.

After a successful spawn/resume: persist its actual agent/session identity, read it back. Move Open → In progress only when that owner acknowledges AND actual execution is evidenced. Stage-child IDs and the Supervisor session stay in notes, separate. Transfer ownership only after the old owner is confirmed stopped or explicitly hands over; retain ownership while a task waits and after completion. Review-only guidance never makes the reviewer the task owner.

Resume a completed/stopped task subagent if supported and ownership remains valid. Otherwise confirm its ownership is inactive/cleared before starting a replacement; it reloads the persistent task record and resumes the owed stage. Never duplicate a quiet task subagent. Before dispatch, re-read the row and claim — overlapping cron runs must not both claim it. Use the runtime's claim/lock mechanism if available; ownership cannot be established safely → leave dispatch pending.

### Task slots and priority

At most **three active tasks per project across all runs**, existing executions included — a task limit, not a three-agent limit. An admitted task keeps its slot through stage completions, handoffs and recovery while its subagent is live; a Blocked task with no live execution holds no slot, and starting it again takes a slot again. A parent task subagent + its stage child = one task. Default: one active stage child per task; yield waiting parents so runtime execution slots remain available to children. Runtime cannot support three chains → run fewer; never create idle parents that prevent children from running.

Serialize admission across overlapping runs via a supported lock or atomic reservation: reconcile task/stage IDs, claims, artifacts, live executions → reserve a slot → dispatch/resume. Count in-flight spawn/resume reservations too; release a failed admission only after confirming no execution started. Safe admission cannot be established → leave pending rather than race another run. Unknown execution state does not free a slot.

Open rows: highest project priority first, oldest first within equal priority. Place in line is plain prose on the row, never a label or separate state. Fill free slots from Open rows after reconciliation; never replace an active task or interrupt its stage merely because priorities changed. Three tasks already active → steer them, don't dispatch another. Respect runtime capacity and model-cost limits when filling slots.

### Recover stalled ownership

Next cycle: read back the promised artifact or inspect the owner's live session for actual activity. Nothing moved → diagnose the failed handoff, send ONE corrected instruction. **Kill-and-restart on a stall (Den, 2026-11-07):** a task subagent with NO runtime activity AND NO new server-side artifact (branch, PR, issue/PR comment, Work Log movement) since the previous sweep is STALLED — steering it and waiting another cycle is a failed sweep. In the SAME sweep: (1) verify server-side that no artifact exists; (2) close the stalled agent; (3) dispatch ONE replacement briefed at the task's CURRENT stage — finished stages are never redone (an approved design is reused, not rewritten); (4) record the kill, stall evidence, replacement on the row and the issue. The replacement's brief carries the speed rule: first artifact fast, any blocker posted immediately, silence is failure. Owner confirmed stopped/failed: resume it first when supported and ownership remains valid. Apply the executor fallback (below) when resume is unavailable or confirmed not to have started execution, and no old child remains live; transfer the claim before dispatching ONE replacement. An uncertain resume result is not permission to replace. An unobservable owner is not a dead owner: record the access problem, do independent work, never duplicate it. Three cycles, same failure: stop identical retries, record cause + exact unblock, escalate the unresolved recovery ONCE with a responsible owner and decision needed. A missed acknowledgment deadline or failed recovery is a new escalation event even if blocker and task counts are unchanged. Recheck the dependency each cycle, resume when it changes; never repeat denied actions without materially new relevant authorization. (Annex A-S6.)

### Available-executor fallback

When a task's current executor (any agent runtime, tool or model) cannot continue, choose a supported fallback rather than ending at a failed resume. Classify the failure first:

- Transient runtime failure, terminated session, unavailable execution environment → another available task subagent/runtime may be used, under the checks below.
- Usage-credit/quota, rate-limit, access denial, spend limit = a REAL GATE, not a fallback trigger. Never invoke the blocked task through another subagent, model, tool, account or route to evade that gate, or probe alternatives for that purpose. A genuine quota gate requires provider-supported capacity restoration or explicitly approved, supported separately billed capacity. Never assume a subagent has an independent credit pool; verify the intended execution is legitimately available before dispatch. Keep denied operations stopped; continue only independent work not subject to that gate.

Quota scope, reported accurately: a Codex quota error does not establish that dot's allowance is exhausted; conversely, a user report of remaining dot credits or visible native-subagent tools does not establish that rerouting the same blocked task is permitted. Record verified capacity separately, preserve the task checkpoint, continue separate permitted work outside the gate. Never probe alternate executors for that blocked task or imply a credit purchase is required.

Before any resume/replacement, recheck current user scope + permissions. Current exclusions and withdrawals override older job bodies, task briefs, stored claims; fallback never revives paused, canceled or excluded work. For an eligible fallback, complete this handoff in the same run when the checks permit:

1. Read the task record, owner, stage children. Resume the owner if supported and able to proceed. If not: confirm the old owner is stopped or explicitly hands over, and no old child remains live, before replacement. An inaccessible owner or uncertain resume result does not prove inactivity.
2. Discover the supported available task-subagent/runtime options. Verify actual capability, task + child capacity, artifact access, existing authorization, cost limit. Tool presence alone does not prove usable capacity. New spending, credentials, access, external data sharing keep their own approval requirements; never switch routes around a denial.
3. Preserve verified state in the Work Log: goal + acceptance criteria, stage owed, branch/head SHA, completed artifacts + tests, recoverable uncommitted work, outstanding review findings, permissions/denials, next step, return destination. Resolve uncertain external-operation outcomes by target readback before replaying. Use supported reads/transfers; never invent missing state or assume local files exist on another executor.
4. Reserve the handoff under the admission/claim rules; spawn ONE replacement task subagent with `dev-workflow` + that handoff. It confirms the transferred claim before stage work, continues from the owed stage, never repeats completed work. Preserve the one-task slot/reservation, persist + read back the returned owner identity, verify acknowledgment + activity under the dispatch contract. Never duplicate the task, issue or schedule.
5. No safe authorized fallback: record the exact capacity/access/ownership gate + smallest restoration decision. Report the failed recovery — never claim handoff or execution; preserve work for resumption.

**Ask once.** Where the loop needs a specific bounded decision from the owner (a reserved class, §4), ask once and continue independent work meanwhile.

## 6. Verify

**Continue completed stages.** On a completion notification or a result found during a scan: read back the stage artifact + acceptance evidence. Task incomplete → use the actual message/resume tool to have its task subagent start the next allowed stage or rework; or record the concrete external gate + resume condition when no work is permitted. Receiving or reporting a stage result is not task completion.

**Steer, then verify.** Send the existing live task subagent a concrete next step, required artifact, check point. Never duplicate it. A Blocked row whose reason has cleared is worked in this run under the run loop — never merely relabeled. Open means not being worked now; it is not proof of execution, permission, resolved gates or delivery, and not a specific appointment time. Comments, status changes, dispatch receipts are not artifact progress (the In progress bar is §5's contract). Set Last updated only to evidenced execution/progress time, never scan time; never refresh it for review-only comments, ownership backfills or Open relabeling — date those observations in the comment. Keep the last artifact URL/SHA + its movement time in the row notes; unknown progress remains unknown.

**Reconcile completion.** Done requires API-read-back merge SHA + recorded Stage 5.5 Design/PRD sync + Stage 6 acceptance evidence. Merge or issue closure alone is not Done; deploy never holds a row open (`dev-workflow`, Stage 6). Reconcile active code-host work into the Work Log without inventing an active owner.

**Merged-PR sweep.** Every run lists PRs merged since the previous run across the currently authorized project's repos — a PR merged with no linked issue is invisible to every other step. A merged PR with no linked issue and no Work Log row gets a row in the same run (status from verified project acceptance, Links = the PR, owner recorded as other-actor/unknown); a merge alone does not prove delivery. A record-less merge touching credentials/secrets paths, deploy workflows, or production routing is additionally flagged by name in the Agents Context rewrite — that class of change never passes silently. (Annex A-S2.)

**Goal-fit sweep — the default is closure.** Every run tests EVERY open row (any status other than Done or Closed) against the project goal statement from the job body — and the presumption is flipped: **the default for every open row is closure.** Closure = setting the row to the board's Closed state; the sweep never deletes a row or its record — a closed row is off the board and stays recoverable. A board that keeps everything tracks nothing. A row stays open only with an affirmative keep-reason, written on the row itself during the sweep, of exactly one of two kinds:

1. **Goal-critical:** the Supervisor is 100% confident the project goal fails without this row, and can name the failure mechanism in one sentence — "without X, Y cannot happen because Z". "Useful", "related", "hygiene", "might need it later", "someone should do it eventually" are not reasoning and do not keep a row. A gate another surviving row depends on earns this keep-reason: without the gate, the surviving row cannot proceed, so the goal fails through it.
2. **Live execution:** work is in flight right now and this row is its coordination surface — a named owner + current activity.

Everything else closes in the same run:

- **No keep-reason → close it**, reasoning written on the row before closing. **A close without its reasoning on the row is a protocol violation and does not count as done.** The reasoning is a dated closure note stating (a) why the row fails the keep test, in one concrete sentence — "not needed" alone is not reasoning; name the ground: duplicate of X, superseded by Y, not goal-critical because <failure mechanism absent>, record-only, or check folded into <task> — and (b) where its record lives (linked issue, document, evidence pack). No external record exists → the closure note itself carries the one-line residual, so nothing is silently lost.
- **The same test applies to the GitHub issue behind the row.** A row closed under this sweep — or with no keep-reason — has its linked GitHub issue closed too, same reason recorded on the issue, unless that issue also backs a surviving row or is the surviving/superseding record for one; a closed issue remains readable, so closing is not deletion.
- Duplicates of another row or issue, rows superseded by a merged change or a newer record, record-only rows (checkpoints, pointers, receipts — their facts live in run logs and handoff documents), rows that merely do not serve the goal: all fail the test, no exceptions — close under the same rule, surviving/superseding record named in the closure note where one exists.
- A row that is really a check inside a larger kept task is not a row: fold it into that task's checklist, close the standalone row.
- NO middle tier: no "backlog — keep", no annotate-and-keep for non-critical work. Doubt resolves to closure, never to keeping: "kept just in case" and "kept-but-doubted" are failures of the test. A closed row that matters later is re-created from its record when it becomes goal-critical or enters live execution.

Closing is the Supervisor's own decision: it fits none of the owner's three reserved classes, so it is never parked as an owner decision or presented as an option menu. One guardrail survives: never close a row whose unresolved safety or financial residual exists only on that row without recording the residual in the closure note first (or, when the residual itself is goal-critical, keeping the row under keep-reason 1, which names it). The sweep's report names the surviving open count + each survivor's keep-reason class (goal-critical / live execution).

## 7. Report

**Run-end continuation check.** Every active incomplete task gets a concise continuation receipt in its Work Log row: verified owner/runtime state + checked time; last artifact + movement time; next executable step; and either current execution evidence, an actual resume/dispatch receipt with acknowledgment state, or the exact external gate + resume condition. An accepted handoff without execution evidence stays pending in this receipt; it does not justify an In progress transition or a progress timestamp. Link existing evidence instead of duplicating unchanged notes; review-only receipts do not advance Last updated.

**Live-lead check (run end).** Re-check before ending: every In progress row has a live subagent; every Open row carries its reason; every Blocked row carries its one reason + this run's fresh attempt. Any In progress row lacking a live subagent is resolved now under the run loop. **A mismatch left at run end fails the run:** an In progress row with no live subagent, or a workable row left unstarted with no reason on the row, means the run reports itself as FAILED (a protocol violation, escalated to the project's main session), never as a completed check with notes.

Owner inaccessible: use the supported coordination tool to ask the owning coordinator to verify/recover that owner — task, last artifact, owed next step named. Record the handoff receipt, acknowledgment state, deadline under the dispatch contract. No coordinator or supported route: report that precise capability gap + smallest required decision to the invoking session; keep only the affected recovery pending. Never repeatedly carry "owner unobservable" as if it were continued execution; never replace the owner until inactivity or handover is verified.

Before ending, reconcile the board: work started this run, Open rows + their on-row reasons, Blocked rows + their one reason each. Execute admitted authorized steps; if none can run, record the evidence for that conclusion + the concrete recovery or resume condition. A board scan, context update or preserved owner name alone does not satisfy this check. Before ending a run, ensure each active incomplete task has a live responsible task subagent or a confirmed continuation action — for a stopped owner use the recovery contract (§5); for a real wait or missing capability, record the exact gate + resume condition. A summary alone does not keep the chain running.

**Continuity handoff to the main session (Den, 2026-11-07).** A run is a snapshot; the project's main session is the continuous owner between runs. The run's report into the main session hands off every live or pending task thread as ACTIONABLE CHECKPOINTS, not status: for each — the task, its lead's identity + verified state, the next expected artifact or verdict, and the exact action the main session takes when it lands (steer on stall under the kill-and-restart test, read back a Stage 4 verdict and merge on PASS, dispatch the owed next stage). The main session adopts those checkpoints as its own work and finishes chains between sweeps instead of waiting for the next run. A handoff that reports status without checkpoints the main session can act on is incomplete — the same failure as a tidy board with waiting tasks.

**Dedupe notifications, not recovery.** An unchanged task count is never a reason to skip recovery. Before deciding "nothing new": consume unread Product Owner guidance; compare each held task's candidate SHA, run/attempt, failure cause, owner acknowledgment, latest artifact movement with the previous check. A changed failure or failed handoff requires diagnosis even when row count and status are unchanged. Incomplete task with no active owner or a failed run → reuse the existing root-cause repair under the claim/resume + three-slot rules; never create a duplicate issue or assume an unobservable owner is dead. Work already running: steer only when needed, check its promised artifact rather than dispatching again. Repeated identical failures use the bounded recovery rule (§5), not repeated spawn/message loops. Notification deduplication never suppresses permitted execution or recovery; a read acknowledgment, reminder or unchanged count is not progress — record actual action receipts, evidence, or the exact gate before ending the run.

**Den's questions are run under this skill (Den, 2026-11-07).** The main session answers the owner's count/state questions in its Supervisor capacity, not from conversation context: ANY question about tasks, subagents, board or PR counts is a status request — first run the fresh board pull + `subagent.list` filtered to this session's chat_id, then answer only from that output, every count naming its source and time. If a source is unavailable (e.g. Notion quota), say "unverified" with the last verified value and its age; a number from memory is never presented as current. The status table/reflection/push mechanics are `dev_workflow`'s "On Den's status request" section; this trigger is what invokes them.

**Reporting.** Message the job's own session chat ONLY, one short line per completed unit: a row set Done with its evidence; a stalled row pushed with what was dispatched; an unstarted item started; a row closed by the goal-fit sweep (`closed <row> — <reason>`, e.g. `closed <row> — duplicate of <X>`); the sweep's surviving open count + each survivor's keep-reason class; a held row whose blocked-sweep reflection is new or changed this run (what was tried, why it still holds); or a blocker/recovery escalation that genuinely needs the project owner, after permitted self-resolution attempts, stating what was tried. A newly missed acknowledgment deadline or failed recovery qualifies even when the original blocker is unchanged; deduplicate only an already-delivered escalation with no new decision or failed recovery. No completed unit + no escalation event = stay silent (the self-edit report in §8 is the only exception). Never narrate partial steps, checks that changed nothing, or Blocked rows that did not change. A status-only run that leaves actionable work unstewarded is a failure; a verified real gate is not permission to push through it.

**Escalation — systemic blockers.** Overrides ordinary silence/own-session reporting. Each run counts Blocked rows, oldest blocker age, root causes. Escalate to the main project session configured in the job if: one cause holds ≥3 rows, verified infrastructure is down, or the Blocked count grows. Missing access = unknown state, not proven infrastructure failure. Send: cause, evidence, affected count, exact unblock, responsible owner. Old blockers still qualify; deduplicate unchanged cause + counts, not the first escalation. A verified infrastructure-down state escalates however it was learned — classifying it as "not a blocked dependency" to justify silence is a closed loophole; silence in the face of a systemic blocker is a protocol violation. Refresh the Agents Context escalation line each run: checked time, Blocked count, oldest age, causes, last escalation. Status renames must not hide blockers. Destination missing or delivery fails: record that failure, notify the invoking session; never silently claim escalation succeeded. (Annex A-S7.)

## 8. Reflect

**Self-improvement (final step, every run).**

1. Work FROM the Agents Context page: recurring failure patterns are recorded there. Scan the Work Log rows + this job's recent runs for REPEATED failure patterns — same kind of stall, misdiagnosis, wasted check, wrong stage recurring across tasks/runs. Find where the agent keeps going wrong across the list; fix that recurring cause in the job's own instructions. Before any self-edit, re-read the patterns recorded on the context page — a pattern earns a self-edit only when recorded there as recurring, never from a single run's impression. New patterns found are written to the context page in the same run (in the closing context-page update). One-off incidents are logged, never edited for. Reflection discipline per the `dev-reflection` skill.
2. Scheduler self-editing authorized + supported → apply the concrete fix to this job with the scheduler tool. Otherwise record the proposed fix + the missing capability/approval; never claim it was applied. HARD LIMITS: schedule, delivery chat, owner, enabled state, and the project parameters in the body (Work Log / PRD / Design / Decision Log links) remain byte-identical; only the loop's working instructions change; a self-edit never expands the job's authority (no new permissions, no release actions, no new chats or projects).
3. Every self-edit is recorded in the same run: a one-line report in the job's own session chat ("self-edit: <what changed> — <why>") even when the run otherwise reports nothing, PLUS a dated entry with the same content in the runtime's daily memory log. No silent self-modification.
4. A lesson that applies to all projects is appended to the `dev-workflow` skill as a lessons/reflection entry — never a rewrite of its core protocol.

**Agents Context (the project's context page).** One per project, titled "Agents Context", under its project hub in the project's notes system; the job body wires its link as a project parameter.

- **Purpose:** the project's local memory — only the current information an agent must not forget to work the project correctly.
- **Keep it short — one screen.** Belongs: current state in 2–3 lines, active fronts, live gates/blockers with their exact unblock, recurring failure patterns, next priorities. Does NOT belong: history, completed-task detail, run logs, evidence — those live in the Work Log and the daily log; link, don't copy.
- **Maintenance:** read first at run start (§1); rewritten after the reflection step at run end — an ordinary run write, like a Work Log row update. Rewriting = compressing: anything no longer true is deleted, not accumulated. Page past one screen → the run that notices compresses it.
- **Reflection link:** the reflection step works FROM this page (above).

## Standing constraints

- Release tags and publishes follow **Release authority — the product owner decides** (§4) — no restatement here.
- Runner/disk/CI faults can require a scoped infrastructure repair task: reuse an existing root-cause task or create one with evidence + acceptance criteria; never duplicate tickets for an unchanged queue observation. Keep only truly dependent steps waiting; never report checks or ticket creation as execution progress.
- Investigate CI queue causes; keep independent work moving. A blocked queue waives nothing: review, exact-commit verification, merge authorization, delivery gates all stand; a local-evidence alternative only where explicitly permitted by the project and the project owner.
- Verify live, never from document audits alone; "unverified" is a hypothesis, not a task.
- Never print secret values anywhere. Observations worth keeping go to the runtime's daily memory log, never the curated long-term memory file.
